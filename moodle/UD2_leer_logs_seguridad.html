Un log de seguridad es el registro estructurado de algo que pasó: quién hizo qué, cuándo, desde dónde y con qué resultado. Es la materia prima del SIEM y la evidencia del informe. Esta sección enseña a leerlos fuente por fuente, con ejemplos del laboratorio; las secciones siguientes profundizan en Windows y en Linux.

Regla de oro: nunca se juzga un campo suelto. Es la combinación (hora + origen + usuario + acción + resultado) y, sobre todo, el patrón (repetición, horario raro, origen desconocido) lo que convierte un evento normal en sospechoso.

CampoPregunta que respondeEjemplo (laboratorio)

Identificador de evento¿Qué tipo de suceso?4625 en Windows · regla 5760 en Wazuh

Normal: lo esperado y habitual (la docente entra desde su puesto en horario de clase). Sospechoso: lo inesperado o de alto riesgo (decenas de fallos seguidos, un acceso de madrugada, un origen desconocido, una cuenta nueva que nadie pidió).

Todas convergen en el SIEM (Wazuh, Splunk), que correlaciona, alerta y permite investigar. Una sola fuente da una visión parcial; varias, la historia completa.

3) Linux: autenticación

En Debian/Ubuntu el fichero clásico es /var/log/auth.log (en RHEL, /var/log/secure). Ojo: Debian 12 sin rsyslog no lo crea; todo está en el diario de systemd y se lee con journalctl.

sudo grep "Failed password" /var/log/auth.log | tail -n 20      # fallos de SSH
sudo grep "Accepted" /var/log/auth.log                          # accesos correctos
sudo grep "sudo:" /var/log/auth.log                             # quién usó sudo y para qué
sudo journalctl -u ssh --since "-1h"                            # lo mismo sin auth.log
# ¿quién lo está intentando más?
sudo journalctl -u ssh --since today | grep "Failed password" \
  | grep -oE 'from [0-9.]+' | sort | uniq -c | sort -rn | head

Señales: muchos fallos seguidos desde la misma IP (fuerza bruta, como el hydra de la actividad 2.2), accesos desde IP desconocidas o a horas raras, usuarios que no deberían existir, sudo inesperado.

5) Cortafuegos

Cada línea dice qué conexión se permitió o se denegó, con origen, destino, puerto y protocolo. Señales: muchos rechazos desde la misma IP, intentos a puertos poco habituales (3389, 4444, 8080), ráfagas de conexiones en poco tiempo (escaneo). En el laboratorio, con nftables:

# regla que registra y descarta (UD4); el aviso aparece en el diario del kernel
nft add rule inet filtro entrada tcp dport 22 ip saddr != 172.21.10.0/24 log prefix "NFT-DROP-SSH " drop
sudo journalctl -k | grep NFT-DROP

6) DNS

Cada consulta registra el dominio pedido, el equipo que lo pidió, la hora y el código de respuesta: 0 = resuelto, 3 = NXDOMAIN (no existe), 5 = rechazada. Señales: dominios largos y aleatorios, muchos NXDOMAIN seguidos (malware probando dominios generados por algoritmo, DGA), dominios recién registrados y volúmenes anómalos desde un solo equipo (posible túnel DNS para sacar datos o controlar el equipo). En el laboratorio, Sysmon registra las consultas de win10 (evento 22) y Suricata las de la red.

8) Nube (para conocerlo; fuera del laboratorio)

Registran cada llamada a la API: AWS CloudTrail, Azure Activity Log y Google Cloud Audit Logs. Se vigila sobre todo la identidad (usuarios, roles y permisos nuevos o cambiados), la creación inesperada de recursos (máquinas para minar criptomonedas) y los cambios de red y seguridad. Campos típicos de CloudTrail: eventTime, eventName, userIdentity, sourceIPAddress.

Práctica rápida (tras la actividad 2.2): con los logs de srvweb y win10, construye una mini línea temporal del ataque de fuerza bruta: primera y última petición, IP, número de intentos, si hubo acceso correcto después y qué hizo esa cuenta. Indica de qué fuente sale cada dato.
