El siem y srvweb son Debian y el atacante es Kali: buena parte de la investigación se hace en la terminal. Esta sección reúne lo imprescindible de Linux con la mirada del analista: dónde está la evidencia, qué comando la muestra y qué indica algo raro. Todos los comandos son de consulta; los que cambian algo están marcados.

1) Dónde está cada cosa

RutaContenidoInterés para el analista
/etcConfiguración (SSH, usuarios, servicios, cron)Cambios no autorizados: /etc/passwd, /etc/sudoers, /etc/ssh/sshd_config
/var/logLogs del sistema y de las aplicacionesInicios de sesión, errores, Apache, Suricata
/home, /rootDatos de usuarios.bash_history, .ssh/authorized_keys (claves añadidas = puerta trasera)
/tmp, /dev/shmTemporales (escribibles por todos)Lugar favorito para dejar y ejecutar malware
/procSistema de ficheros virtual con los procesos en marcha/proc/<PID>/exe y cmdline: qué ejecuta de verdad un proceso
/etc/systemd/system, /etc/cron*Servicios y tareas programadasPersistencia

2) Comandos básicos de lectura

pwd; ls -la /var/log                 # dónde estoy y qué hay (con permisos y fechas)
less /var/log/apache2/access.log     # leer por páginas (/ busca, q sale)
head -n 20 fichero; tail -n 50 fichero
tail -f /var/log/suricata/fast.log   # seguir en directo
grep -i "failed" fichero             # buscar texto (-r recursivo, -c contar, -v excluir)
find /etc /var /tmp /home -type f -mmin -60 2>/dev/null      # ficheros cambiados en la última hora
find /tmp /dev/shm -type f -perm -u+x 2>/dev/null          # ejecutables en temporales

3) Usuarios, grupos y privilegios

id; whoami; groups
awk -F: '$3 == 0' /etc/passwd        # cuentas con UID 0 (solo debería salir root)
awk -F: '$3 >= 1000' /etc/passwd      # cuentas de personas
getent group sudo                    # quién puede usar sudo
sudo ls -l /etc/passwd /etc/shadow   # shadow solo debe leerlo root (640 o 600)
last -n 20; lastb -n 20              # últimos accesos correctos y fallidos

Riesgos: demasiados usuarios con sudo, cuentas nuevas sin explicación, un segundo UID 0, contraseñas débiles o compartidas.

4) Permisos y propietarios

Cada fichero tiene permisos de lectura (r = 4), escritura (w = 2) y ejecución (x = 1) para propietario, grupo y resto: rw-r--r-- = 644; rw------- = 600. Se cambian con chmod, chown y chgrp (estos sí modifican).

ls -l /etc/ssh/sshd_config           # -rw-r--r-- root root: solo root modifica
find / -perm -0002 -type f -not -path "/proc/*" 2>/dev/null   # escribibles por todos
find / -perm -4000 -type f 2>/dev/null                       # binarios SUID (escalada de privilegios)

Malas prácticas: chmod 777, claves privadas legibles por otros (deben ser 600 y la carpeta ~/.ssh 700), configuración con propietario incorrecto. Principio de mínimo privilegio.

5) Procesos

ps aux --sort=-%cpu | head           # los que más CPU usan
pstree -p                            # árbol padre → hijo
pgrep -a sshd
sudo ls -l /proc/<PID>/exe; sudo cat /proc/<PID>/cmdline | tr '\0' ' '
sudo ls -l /proc/*/exe 2>/dev/null | grep deleted           # binario borrado pero aún en marcha

Sospechoso: procesos que se ejecutan desde /tmp o /dev/shm, consumo de CPU disparado (minero), cadenas padre-hijo raras (un servidor web que lanza bash), nombres que imitan procesos del sistema.

6) Servicios y persistencia con systemd

systemctl list-units --type=service --state=running
systemctl list-unit-files --state=enabled          # lo que arranca al iniciar
systemctl status ssh; journalctl -u ssh -n 50
ls -lt /etc/systemd/system/ | head                  # unidades añadidas recientemente
sudo crontab -l; ls -la /etc/cron.*                 # tareas programadas

Una unidad .service desconocida con Restart=always y WantedBy=multi-user.target, que ejecuta algo de /tmp, es persistencia de manual (MITRE T1543.002). Lo mismo con una tarea de cron inesperada (T1053.003). Wazuh las detecta con FIM sobre esas rutas.

7) Red

ip -br addr; ip route                # interfaces y rutas
sudo ss -tulpn                       # puertos a la escucha y qué proceso los abre
sudo ss -tnp state established       # conexiones activas
sudo lsof -i -P -n                   # ficheros de red abiertos por proceso
dig <dominio>; ping -c 3 172.21.10.30       # resolución DNS y alcance
curl -I http://172.21.10.30          # ¿responde el servicio?

Sospechoso: puertos a la escucha que nadie ha abierto (4444, puertos altos), conexiones salientes repetidas hacia la misma IP o dominio (posible canal de mando y control), un proceso inesperado detrás de un puerto. Recordatorio: TCP establece conexión y garantiza la entrega (SSH, HTTP); UDP no (DNS, streaming).

8) Cortafuegos y SSH

HerramientaUso
nftables (nft list ruleset)El cortafuegos moderno de Linux; es el que se usa en el laboratorio (UD4)
UFW (ufw status verbose)Capa sencilla, habitual en Ubuntu
iptables / firewalldAntiguo pero aún presente / gestor habitual en RHEL

Endurecimiento de SSH (en /etc/ssh/sshd_config, y después sudo sshd -t para validar y sudo systemctl reload ssh; modifica el sistema):

  • Autenticación por clave y PasswordAuthentication no (frena la fuerza bruta de la 2.2).
  • PermitRootLogin no y acceso solo para usuarios o grupos concretos (AllowUsers/AllowGroups).
  • Cortafuegos que solo deja entrar SSH desde la red de gestión.
  • Cambiar el puerto 22 reduce el ruido de los escaneos, pero no es una medida de seguridad por sí sola.
  • Revisar los logs de SSH y aplicar actualizaciones.
Antes de endurecer SSH en una máquina remota, deja otra sesión abierta y comprueba que puedes entrar con la clave: un error en sshd_config o en el cortafuegos te deja fuera.

Práctica: triaje rápido de srvweb (10 minutos, solo lectura). Responde con el comando y la salida que lo prueba: ¿qué cuentas pueden ser root?, ¿quién entró en las últimas horas y desde dónde?, ¿qué escucha en la red y qué proceso lo abre?, ¿hay ejecutables en /tmp o /dev/shm?, ¿hay servicios o tareas de cron añadidos recientemente?, ¿qué ficheros de /etc cambiaron hoy? Después compáralo con lo que muestra Wazuh.
